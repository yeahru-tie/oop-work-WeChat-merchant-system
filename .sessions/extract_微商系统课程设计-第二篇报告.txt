一、项目需求的进一步理解
1.1 需求理解的推进
第一篇报告完成了需求的初步梳理，确立了交易闭环、六层结构与主要技术选型。本篇在既有结论之上，把各功能的业务规则细化到可执行的粒度，并明确边界条件与异常情形，为概要设计提供依据。
1.2 核心业务的规则细化
（一）账号与登录
注册时账号唯一；密码加盐哈希后存储，盐值随机生成并随用户记录保存，不存明文；新注册用户默认角色为「顾客」。登录时服务端按账号取出盐值，对输入密码做同样哈希后比对，成功则返回用户信息与角色。店主账号由建库时预置，不开放前台注册，避免权限失控。
（二）商品与购物车
商品只有店主可新增、修改、上下架；下架商品对顾客不可见、不可加购。购物车存储于服务端；同一用户对同一商品重复加购时合并数量；数量必须为正整数；结算时支持勾选部分条目。
（三）促销与结算
多个促销同时生效时按固定顺序计算：先打折 → 再满减 → 最后用券，顺序写入配置文件。促销可指定适用商品（多对多关联），结算时仅命中的促销生效。库存校验与扣减必须在服务端事务内原子完成；客户端只做金额预演算并标注「预估」，实际金额以服务端返回为准。
（四）订单与售后
订单状态流转：待付款 → 已付款 → 已完成 / 已取消；已付款订单可发起售后，进入售后中，审核通过则回补库存并退款，拒绝则恢复为已完成。「已付款」由顾客点击确认触发，属于对支付环节的模拟。
（五）店主端
店主角色承担商品维护、促销配置、售后审核、订单只读四类操作。系统只有一套客户端程序，登录后按角色动态挂载界面，不做独立的店主端程序。
1.3 边界与约束的进一步说明
系统为单店经营、多用户访问；明确不做多商家入驻、真实支付、移动端与浏览器端、商品评价、收货地址、收藏夹。客户端运行在用户机器上，其计算结果可被篡改，故「客户端可预估、服务端必须复算」是贯穿全系统的安全约束。
1.4 非功能需求的细化
并发：多用户同时结算同一商品不得超卖，由数据库条件更新保证正确性。
扩展：新增促销玩法不修改核心交易代码，由策略 + 反射实现。
部署：客户端与服务端为两个独立进程，协议不依赖回环地址，可拆分到两台机器。
界面：提供 3 套主题，切换仅影响表现层，不触及业务层。
二、相关技术讨论
2.1 C/S 与 B/S 结构
C/S（客户端/服务器）结构中，客户端为独立安装的桌面程序，与服务端直接通信；B/S（浏览器/服务器）结构中，客户端是浏览器，通过 HTTP 访问 Web 服务器。二者的差异决定了各自的适用场景：

本项目的选择是 C/S。任务要求 PC 桌面应用、自定义 TCP 协议与 Swing 界面，这正是 C/S 的典型形态；更重要的是，C/S 才能直接练到 Socket 通信与自定义协议这一底层原理，B/S 会把这些封装在 HTTP 与容器之后。
2.2 Web 服务与 JavaEE / JSP / JavaScript（B/S 技术族）
JavaEE 是服务器端企业级规范（含 Servlet/JSP/EJB），JSP 是服务器端动态页面技术，JavaScript 是浏览器端脚本语言，Web 服务（SOAP/RESTful）是服务之间通过 HTTP 交互的方式。这些技术共同服务于 B/S 架构。
本项目不使用它们，原因是架构形态不同：本项目客户端是 Swing 桌面程序而非浏览器，服务端通过自定义 TCP 协议而非 HTTP 通信，因此不需要 JSP/JavaScript 渲染页面，也不需要以 Web 服务对外暴露接口。这些技术属于「经过比较后排除的候选方案」，排除理由清晰——理解它们，是为了说明本项目的选型边界是明确且可论证的。
2.3 MVC框架
MVC 将程序划分为 Model（数据与业务）、View（界面）、Controller（调度）三部分，使界面与业务解耦。本项目客户端按 MVC 组织：View 只负责展示与采集输入，Controller 负责事件调度，业务规则全部放在 Service 层，不写入界面代码。服务端虽无界面，但同样遵循「业务层与表现层解耦」的思想。需要说明的是，本项目不引入 Spring MVC 等现成框架，而是从原理层面自行实现分层，以避免被框架封装遮蔽，只学会调用而学不会设计。
2.4 持久层
持久层负责对象与关系数据库之间的映射，是本项目理解 ORM 本质的关键。演进路径为：先手写 JDBC（Connection/PreparedStatement/ResultSet）完成「对象存成表、表读回对象」的完整过程，再抽象出 DAO 接口隔离业务层，后期引入 MyBatis 以演示「持久层实现可替换」的柔性。
数据库采用 SQLite 起步（零部署、单文件便于交付），同时保留切换 MySQL 的能力：两套建表脚本分别处理自增语法差异，分页统一使用 LIMIT ? OFFSET ?，时间统一存 ISO-8601 字符串，使方言差异收敛在建表脚本中、DAO 代码不分叉。

2.6 并发与互斥
多用户同时抢购限量商品时，若扣减库存采用「先查询、再判断、后更新」三步式实现，两个线程之间会形成竞态条件，导致超卖。本项目的方案是数据库条件更新——把判断与扣减合并为一条原子 SQL：
UPDATE t_product SET stock = stock - ? WHERE id = ? AND stock >= ?
执行后检查影响行数：返回 1 表示扣减成功；返回 0 表示库存不足，回滚事务并返回失败。JVM 层按商品编号分段加锁是性能优化而非正确性保证——它只在单进程内有效，一旦服务端多实例部署就会失效，而数据库条件更新依然有效。本项目还计划以「超卖复现实验」作为并发正确性的直接证据。
2.7 同步与异步通信
同步通信是请求—应答模式：客户端发出请求后阻塞等待应答，实现简单、结果直观。异步通信则允许请求发出后不等待，结果通过回调或事件返回。本项目采用「同步为主 + 推送通道」：核心功能以同步方式交付，保证进度；服务端在订单状态变更等事件发生时，通过长连接上的推送通道主动通知客户端，作为异步能力的落地点。

4.3 个人收获与反思
两周以来，通过需求分析与本篇设计，笔者对 C/S 架构、自定义通信协议、并发互斥与设计模式有了从概念到方案的落地理解。最大的收获是认识到「底层原理优先于框架」——先手写 JDBC 与自定义协议，才能真正理解映射与粘包半包，框架只是这些原理的封装。
反思在于，最初对多店、真实支付等功能有求全的冲动，经范围管理明确「不做清单」后才聚焦到真正的考点上。这提醒笔者：边界清晰的中等规模系统，其工程价值高于边界模糊、处处半成品的大系统。
