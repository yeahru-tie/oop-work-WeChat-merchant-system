## 推进方式

按步骤和可验收结果推进，不按交付日期排期，也不要求用户先说明技术熟悉度。每轮默认只完成一个小任务：先说明目标与边界，完成后验证、更新日志、交付结果，再等待用户选择继续或调整。路线图不等于一次性授权全部实现。

用户已将技术选型交给代理；功能范围、界面效果和交易规则仍需与用户讨论。具体边界见[决策记录](决策记录.md)。业务细节仍在[需求文档](微商系统课程设计-需求描述与技术讨论.md)维护，日志不另定需求。

用户最新要求：最终交付应有精美 UI，但 MVP 阶段先推进功能和正确性。当前界面只保证可读、可用和状态明确，不视为最终设计；S14 专门讨论并打磨视觉效果。

## 每轮交付格式

开始时说明“本轮目标、涉及内容、通过标准、不在本轮范围内的后续项”。完成时提供：

1. 做成了什么，如何运行或查看。
2. 实际验证及结果，哪些仍未验证。
3. 需要用户查看的效果或决定的问题。
4. 更新到哪份日志，以及下一项建议任务。

“实现并验证通过”与“用户接受”分开记录。用户发现不符合预期时，下一轮先调整当前功能；不带着未解决的偏差继续扩展。

## 变更和恢复

出现新需求时，先说明相对现有方案的变化、影响和取舍，再由用户决定是否加入。记录被替代的决定，不抹去历史依据。

保持一个任务的改动可独立检查、验证和提交；提交和推送遵循用户授权，不为生成日志自动提交。修复问题不混入无关重构，不覆盖用户已有改动；禁止用清空目录或重写历史作为常规回退方式。
