### 4.3 模式落地

统一促销接口接收价格上下文并返回优惠结果与明细。各策略实现具体算法，装饰器按确认顺序包装计算；受控配置和反射工厂加载服务端已有类。新增促销的验证应证明原有策略结果不变。

不要为“展示模式”强行重复计算或重复扣减。C++ RTTI、工厂注册表与 Java 反射有不同机制，不能无条件宣称互相替代后仍满足相同课程考点。

商品 1001 与购物车 1002/1007/1008 的条目扩展 `promotion` 金额快照：`configurationVersion`（无配置为0）、`originalUnitCents`、`reductionCents`、`discountHundredths`（1..1000）、`afterReductionCents`、`estimatedUnitCents`。金额均为整数分；无生效活动返回直降0/折扣1000及原价，已保存但未生效仍带配置版本。DTO 严格校验字段、整数、原价及步骤一致性；旧无此字段应答兼容为未取得优惠信息，不伪造活动。

商品/购物车内价格和配置在同一数据库快照、同一时刻计算。购物车仍不占库存，展示原价、直降、折扣和预估合计；更新/失败期间保留既有禁用/清空规则。配置变更不增加购物车内容版本；下一次读取按新配置/时间重算。此为刷新时预估，不锁价、不成交；1009 的券/正式报价确认留给 S10/S11。

管理窗口使用后台串行控制器，实际 DAO/计算不在 EDT；保存结果未知或版本冲突先重新载入，不自动重放。退出/失效关闭本次窗口的控制器，忽略迟到结果。预览按当前商品价和显式草稿参数计算，忽略启停/时间并明确标注“未保存参数试算”，不改变活动或交易数据。

#### 本地只读试算工具（S09.2 原始交付）


本轮已交付服务端纯计算、可解释明细及 `scripts/preview-promotion.ps1` 本地只读预览命令。预览按商品编号读取服务端数据库当前单价，再应用显式试算参数；不接收自报商品价，不保存或发布活动，不占库存、不创建订单或核销券，不增加网络操作码或管理页面。

复用同一计算器供预览与后续业务调用。直降先截到零，统一折扣先逐件 HALF_UP 到整数分，再以精确大整数乘数量，避免总额溢出；不逐件循环。无优惠/10折返回原价。展示原价、各步前后金额、实际优惠额及预估总额，配置直降超过单价时仅展示实际减免。

这是本地开发核对工具，读取已有最新模式库，不初始化/迁移；不是商家管理入口。允许正整数数量进行纯金额试算，库存仅作只读参考，不表示有购买资格。正式管理入口和生效活动现已在 S09.3—S09.5 接入；工具本身仍不发布。旧三款演示活动不会自动成为有效活动。

### 5.1 结算事务

S11结算请求包含 checkoutKey（小写UUID业务防重标识）、cartVersion、quoteDigest、couponId（个人券ID或null）及非空itemIds。身份来自服务端会话，不相信客户端自报 userId 或最终价格。

同一用户同一 checkoutKey 成功或明确业务失败后，无论重复点击、重试或重新连接，均返回原终态（成功含原订单）。相同键但业务参数不同应返回 IDEMPOTENCY_CONFLICT。先查该用户该键的既有记录，再验证当前购物车，避免原购物车清空后重试被误报空车。

以下核心操作在同一个数据库事务内完成：

1. 验证用户、购物车内容/版本、价格与促销、券资格。
2. 按商品固定顺序扣减库存。购买量 q 必须为正整数；执行 `stock=stock-q WHERE product_id=? AND stock>=q` 的参数化更新，检查每次影响行数为 1。
3. 创建订单和订单明细，保存历史商品与优惠金额快照。
4. 将券从可用原子更新为已使用，必须检查更新结果。
5. 清理本次成交条目并保存 checkoutKey 对应结果，设置数据库唯一约束防重。
6. 任一环节失败则回滚全部交易操作；已知业务失败仅提交该键的失败结果，不扣库存/用券/建单/删车。SQL或提交异常按未知结果核对；全部成功才提交交易。

提交成功后返回订单号和成交结果。若响应丢失，用户使用原 checkoutKey 查询或重试。不能看到超时就换一个新键再次购买。

S12技术核对要求：本地待核对记录只能在对应终态已被当前有效界面状态接收后清理。取消/账号切换/关闭导致终态回调失效时，保留原记录；交接完成后的文件清理仍在后台执行，不在EDT等磁盘。数据库忙锁使用已有3秒有界等待，不自动重放网络写请求；写入或提交异常仍按未知结果查询/原键手动重试，不以BUSY代替库存不足。竞争与进程终止测试均使用独立临时库并核对最终订单、明细、库存、券、购物车和请求终态。

交易完成事件可以在提交后通知统计模块，但不能异步补写唯一订单记录。第一版如只使用内存队列，应说明进程退出可能丢失通知，统计可从订单重建。

## 6. 通信协议候选规范

这是本项目提出的协议v1，不是PPT原文。探测、商品、身份、购物车、S10券/报价及S11成交/订单及S13申请/查询已固定；消息现已按UI25接通。数据库版本独立，当前v8，已知v1—v7由启动/init先原版本备份再原子升级；只读查询不迁移。

### 6.1 帧与通用字段

S04 固定以下通用契约；S05 商品及 S07 身份复用这些帧/字段，body见各实施基线；结算和订单现已固定于§5。

- 当前仅监听 IPv4 回环 `127.0.0.1:18765`，不暴露外网；两端可通过启动脚本 `-Port` 同步调整端口。
- 4 字节大端正文长度＋严格 UTF-8 JSON 对象，正文 1—1048576 字节。无完整下一帧时的 EOF 表示正常断开，半帧 EOF 是错误；非法长度/编码/JSON 直接断开，不猜测后续报文边界。
- 必填 version（正整数）、type（REQUEST/RESPONSE）、requestId（非空字符串，最多 128 字符）、operation（整数）、sessionToken（游客 null，登录后为最长 4096 字符的字符串）、body（JSON 对象）。当前 version=1；应答另有非空 code、message 字符串。
- 预留诊断操作 `1000 PING → 2000 PONG`；当前请求操作范围 1000—1999，应答为对应请求＋1000。业务操作未实现时返回 OPERATION_UNSUPPORTED，不伪造成功。
- PING 无需登录，body 必须为空；只证明通信应答，不证明交易就绪，也不延长会话。S07 已使用 sessionToken，由服务端校验身份/角色，不能只检查字符串存在。
- 同一连接串行请求；客户端校验应答版本、类型、requestId、operation、code 和服务标识。错误或超时后关闭连接，下次用户操作重新连接；不自动重放请求。
- 建连超时 2 秒；应答完整帧共享 5 秒读取期限，不按每收到一个字节重新计时。服务端每帧最多等待 30 秒（含空闲等待），最多同时处理 16 个连接，超限新连接关闭。
- 已能识别的非兼容版本返回 VERSION_UNSUPPORTED 后关闭；结构本身非法则无法可靠关联，直接关闭。已识别 PING 参数非空返回 INVALID_ARGUMENT。
- UI 在后台执行连接检查，取消/关闭窗口会关闭 Socket；取消只结束本地等待，不保证服务端未收到原请求。当前是只读探测，未来交易写请求仍必须独立防重。

请求样例（长度为下列紧凑 JSON 的 UTF-8 字节数，不包含四字节头）：

```json
{"version":1,"type":"REQUEST","requestId":"probe-1","operation":1000,"sessionToken":null,"body":{}}
```

成功应答样例：

```json
{"version":1,"type":"RESPONSE","requestId":"probe-1","operation":2000,"sessionToken":null,"body":{"service":"merchant-server"},"code":"OK","message":"pong"}
```

后续业务约束：requestId 只标识一次网络请求；checkoutKey 独立标识一次结算，重试时保持后者稳定。超时是结果未知，未来结算用防重键查询。UI06 已固定有效会话可跨 TCP 重连；服务端重启/过期会在带凭证请求时拒绝，客户端清理身份。不能因游客 PING/商品可用跳过私有权限，不自动重放写操作。

PPT 的操作码示例中包含商品编号。候选协议将商品编号放 body，避免编码位数限制。如果老师要求严格照用示例，应在编码前调整并固定，不在两端各自解释。

### 6.3 成功与失败分离

应答码表示“是哪项操作的应答”，code 字段才表示结果；例如 2003 不再单独代表“必然成功”。

通用code沿用S04—S08。S10领取新增PAUSED、NOT_STARTED、EXPIRED、SOLD_OUT；草稿/发布管理本地服务另有CONFIG_CHANGED、PUBLISHED_LOCKED、NOT_PUBLISHED。报价资格在OK应答内用couponStatus表达，不可用应付为null，不能把OK误作可成交。S11的1003在OK信封内用receipt.state=SUCCESS/FAILED表示已核对终态，失败可为PRICE_CHANGED/COUPON_INVALID/CART_CHANGED/OUT_OF_STOCK等。同键不同参数以IDEMPOTENCY_CONFLICT拒绝，SQL或提交异常返回RESULT_UNKNOWN；均不能自动换键。1010 BY_KEY可返回SUCCESS/FAILED/NOT_FOUND/UNKNOWN；NOT_FOUND不代表先前请求不会提交。DETAIL按归属无记录为NOT_FOUND；LIST只返回本人摘要且按订单ID降序、最多100条，详情单独读取。

S13的1004在OK内返回申请receipt.state=SUCCESS/FAILED；SUCCESS只表示原申请已保存，application.status才区分待审核/批准/拒绝/完成，不等于退款成功。明确失败NOT_FOUND/STATE_CHANGED按键保存终态，同键不同参数以IDEMPOTENCY_CONFLICT拒绝；SQL/提交异常RESULT_UNKNOWN须原键核对，1015 BY_KEY的NOT_FOUND仍不能当成肯定未提交。管理员本机服务返回STATE_CHANGED/STOCK_RESTORE_FAILED等，失败须重载，不暴露SQL。

错误应可展示给用户，同时服务端保存排查信息；不得把 SQL、密码或内部堆栈直接显示到普通用户界面。

### 6.4 消息功能的协议边界

S16契约已实现（UI25已确认，生成及两端界面已接通）：1016 LIST_MESSAGES请求`{limit,offset}`、1017 READ_MESSAGE请求`{messageId,limit,offset}`；响应操作码2016/2017，成功code为OK。返回`InboxPage{items,limit,offset,hasMore,unreadCount}`，条目含messageId/kind/title/text/createdAt/read/orderId/productId，按ID倒序。标题1—80字、正文1—2000字且非空白，均为纯文字；页长1—100，偏移非负；未知字段及类型强制转换拒绝。ORDER/RETURN关联本人订单，ANNOUNCEMENT可关联商品，不能同时关联订单和商品。

基础存储为v8 notifications/message_reads，v1—v7先原版本备份再原子升级，v8只验证。私有消息只能本人读取/标读，公开公告每个买家独立已读；管理员不能用买家消息接口。列表查询使用peek不刷新30分钟空闲计时，明确标读属用户操作。重复标读安全，失败可刷新核对，不自动重放。读取本身不生成通知。UI25已确认：登录后空闲即查，此后15秒检查；打开即标读；全部买家含以后登录账号可见立即公告，发布保留原文无改/撤回入口，可关联商品；不补造旧交易通知。事件通知在原业务事务内写入，失败整体回滚；重复终态不重复通知。原队列忙碌、成交确认及待核对提交期间不插入自动检查。

D14 采用客户端后台定期查询站内消息，保持单连接最多一条在途请求的同步模型；消息检查与其他网络任务有序执行，不能在 UI 线程等待。消息1016/1017契约及权限如上；管理端发布沿用本机应用服务，不增加远程管理接口。第一版没有额外推送连接或退出后的系统通知。

客户端：View→Controller/ClientApplicationService→Transport。

### 7.3 S08 基础购物车实施基线

- UI08 用户已确认：游客可浏览，点击加入或进入购物车先打开登录；登录后回原位置，由用户再次点击加入，不保存或自动执行游客写操作。购物车页登录后加载本人内容；退出/身份失效立即清除私人界面，切换账号不得显示前一个账号内容。
- 商品页选择正整数数量，同品累加。UI11 将购物车改为带图片的响应式卡片网格，数量与移除直接在对应卡片操作：步进或输入整数后回车/失焦提交，数量改动自动保存，不设置下方独立保存/移除区。保存期间禁用重复写操作并标明更新中，失败/取消仍须刷新核对。加入及增加后的总数量不得超过当前库存；库存下降后允许减少旧数量或移除，保留条目并标出库存不足，不静默减量。购物车不预占或扣减库存。
- 当前单价/库存来自商品表，条目保存数量与归属；展示单价、数量、小计、原价合计。金额使用整数分，客户端精确整数计算，不显示虚假优惠或结算按钮。商品删除暂受外键限制，不增加管理后台。
- 技术基线：每个买家一份持久化 cartVersion，同品唯一条目，条目编号不复用。所有请求从有效 BUYER 会话取用户；禁止 userId/ownerId/自报价格等额外字段，修改/删除同时限定本人 itemId。
- 查询/写成功均返回完整 `{cartVersion,items}`；items 按 itemId 升序，基本字段 itemId/productId/name/priceCents/stock/quantity，S09 增加 §4.4 的 promotion 快照。单次最多 100 种商品，达到上限明确 CART_LIMIT，不截断私人内容。数字严格整数；数量 1..2147483647，编号正 long，版本非负 long。小计/总额用精确大整数，避免溢出。
- 写操作带所见 cartVersion；服务端在同一 IMMEDIATE 事务内检查版本、商品/库存/归属，写条目并增加版本后读取结果，最后提交。旧版本返回 CART_CHANGED；无权条目统一 NOT_FOUND，不能读改他人数据。参数/库存/版本失败整体回滚，库存不改变。SQLITE_BUSY/LOCKED 返回 BUSY_RETRY，不自动重放写请求。
- 超时/取消或应答损坏不能代表未写入：清除陈旧购物车并提示先刷新核对，刷新成功后才可再次修改；同版本重复/并发请求至多一个成功。同账号多窗口冲突需刷新再操作，不静默覆盖。
- UI13 修正加入库存拒绝后的恢复：收到 OUT_OF_STOCK 明确拒绝时，自动只读查询购物车一次，读取成功转可用状态并保留商品页选择/数量，允许用户改数量后再次点击加入，不自动重发原请求。空车与已有同品都须反复验证，新增数量与现有数量仍累加校验。恢复读取失败/取消/身份失效时不恢复未经验证的可写状态；结果未知不进入该自动恢复分支。
- S08的v3新增购物车，S09的v4新增promotions；S10的v5新增券活动/个人券及发布条款锁定触发器，S11的v6新增订单/明细/成交结果和used_order_id，S13当前v7新增售后历史/申请终态/模拟退款及部分唯一索引。空库原子建最新模式，已知v1—v6先备份再原子升级，保留原数据，已有v7只验证不补种；只读查询不升级。
- 验收：游客/错误角色/过期拒绝，A/B 归属、伪造字段/他人条目、非法数量、同品累加、库存变化、版本冲突/并发/回滚、断线不重放、退出清界面、取消迟到结果、重登及服务重启恢复、v1/v2 备份迁移均须验证。只交付 S08，不实现报价、优惠券、订单或成交。

- 验证真实商品应答、精确金额/中文、坏字段与关联错误、后台响应/重复点击抑制/取消/关窗/重试，以及打包后的真实窗口；不借用运行数据库删除商品来制造空列表测试。

### S07 身份基线（已实现并验证）

- UI05 确认预置两个买家及一个管理员，暂不注册；UI07 随后要求管理端完全取消游客入口，必须先登录再进入管理窗口，连运行状态页也不提前显示。买家暂保留商品游客浏览；登录前后的可见功能差异留待私有功能实现前继续讨论。既有未实现业务仍明确未实现。
- 预置账号为 buyer_a、buyer_b、shop_admin，角色由服务端数据库决定，客户端不能传 userId/role 提权。公开课程演示口令只在 README 指南说明，数据库与种子 JSON 仅保存加盐散列，不记录口令/令牌日志；它们不是用户的真实密码。
- 采用 JDK PBKDF2WithHmacSHA256、600000 次迭代、16 字节随机盐、32 字节结果及恒定时间结果比较，不自行实现散列算法。参数及格式严格验证；用户名/口令长度有上限，失败使用统一身份错误；哈希计算在后台。
- 数据库模式升到 v2，新增 users。已知 v1 先创建一致性备份，再在单一事务内迁移/写演示账号/升级版本；商品不重建、不重置，失败回滚。已有 v2 只验证，不覆盖账号散列/禁用状态或补回删除账号；未知版本仍拒绝。
- UI06 已确认会话可跨短暂 TCP 断开续用，按服务端验证的请求更新最后活动时间，空闲 30 分钟失效；服务端重启全部失效。客户端仅内存保存，关闭不保存状态/口令；明确退出撤销服务端令牌。网络失败不自动重放登录或写请求，退出失败也清除本地身份并明确提示。
- 令牌使用 SecureRandom 生成 32 字节，服务端仅内存保存其 SHA-256 验证值及身份；数量有界、失效清理，不将随机令牌当密码做昂贵散列。当前仍仅本机回环课程演示，不宣称已有公网加密部署。
- 固定 LOGIN 1006/2006（body 仅 username/password）、LOGOUT 1011/2011（空 body）及 CURRENT_USER 1012/2012（空 body）；通用 sessionToken 承载凭证。登录成功返回令牌和公开身份；查询身份验证伪造/失效令牌、归属和角色，不能用客户端自报身份。错误包括 INVALID_CREDENTIALS、UNAUTHENTICATED、FORBIDDEN、BUSY_RETRY，数据库故障使用通用 INTERNAL_ERROR。
- 买家沿用独立小登录窗口。服务端按 UI07 启动只创建管理员登录窗口；只有服务就绪且身份经验证为 ADMIN 才创建/显示管理窗口，买家账号/错误口令/未登录不得进入。管理窗口本身拒绝无管理员身份构造，不能通过按钮解锁替代入口门禁。
- 管理员退出或会话失效时，销毁管理窗口及其中内容，再返回登录入口；再次验证成功创建新的管理窗口。登录入口取消/关闭则结束整个服务端，关停 Socket、任务和定时器；迟到验证不得重新打开管理页。后台商品服务与管理界面身份分开，返回登录不踢掉买家连接，关闭程序才停止服务。启动失败只显示禁用登录的通用错误入口，不退回游客管理窗口。
- 私有数据在退出/身份失效时清理，买家游客商品暂可继续浏览。本身份步骤不实现注册、改密码、购物车或真实受理/公告；后续 C12/UI08 已允许进入 S08，购物车规范统一见 §7.3。

密码参数依据 [OWASP 密码存储](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) 中 PBKDF2-HMAC-SHA256 的建议，调用 [JDK SecretKeyFactory](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/javax/crypto/SecretKeyFactory.html)。选择当前 JDK 已有实现以保持本机部署简单，不声称 FIPS 认证；随机会话及服务端保存验证值的理由参见 [OWASP 会话说明](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)。

## 9. 用例和 UML 修订要求

参与者至少有买家；如果采用人工处理售后，增加管理/受理人员或明确模拟处理机制。商品初始化工具不是自动成为完整管理员角色。

建议用例：查看商品、管理购物车、查询报价、结算、查看订单、申请退货、查看处理结果、切换 UI 风格。

如果使用 UML include，箭头应从包含用例指向被包含用例。结算可包含“校验购物车”和“计算成交价”，不把结算之前所有购物车操作都当成每次结算必然执行的子用例。无券结算不必包含实际券核销。

Mermaid 流程图可辅助说明，但不能仅贴上 include 标签就称作严格 UML 用例图。最终提交图种与格式以课程要求为准。建议补全促销类图、结算时序图、订单/售后状态图，并保证与代码相符。

## 10. 技术讨论与学习

技术熟悉度由本人填写，不能预设：Java、C++、GUI、SQL、Socket、线程、事务、设计模式、反射、UML。先检查现有项目、依赖和可用工具，再最终选型。

建议学习与实现顺序：

1. 两端 Socket 发一条请求并收到应答，理解长度前缀与完整读取。
2. 服务端通过持久层查询商品，桌面端展示真实数据库数据。
3. 实现用户隔离和购物车，再固定促销计算样例。
4. 完成原子结算、防重与并发验收。
5. 完成售后和主题，视时间加入观察者/后台统计通知。

Java 反射实例化优先使用 `getDeclaredConstructor().newInstance()` 等构造器 API，不继续推荐已弃用的 `Class.newInstance()`。反射加载与异常处理需受控。

采用手写持久层不自动“加分”，使用 MyBatis 也不自动违背课程目标。关键是层次清楚、能够解释映射与事务、符合老师另行明确的限制。
