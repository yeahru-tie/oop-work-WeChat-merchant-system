## 1. 项目定位与证据边界

本项目采用 **PC 桌面客户端＋服务端**，实现单店、多用户的购物交易系统，展示分层架构、TCP/IP 通信、面向对象设计、数据持久化、并发与互斥。

本文区分三类信息：

- **PPT 明确内容**：能定位到原始页码。

- **待确认事项**：原始材料没有说明、却会影响实现的细节。

技术示例不等于强制选型；对评分的理解不等于评分承诺。

## 3. 为什么本项目采用桌面 C/S

用户已确认此架构，也符合 PPT 对避免过度封装、理解系统机制的教学倾向。它便于分别运行客户端和服务端，展示消息内容、业务处理、数据库变化，以及多个客户端同时操作时的正确性。

C/S 不天然比 Web 更适合所有项目。HTTP 也常运行在 TCP 上，Web 也能实现清晰分层。当前选择的依据是用户目标与课程展示需要。

Java、C++、C# 均在语言不限的范围内。建议选最能理解和完成的一条路径，再用实际实现展示深度。跨语言会增加构建、调试与协议适配成本，只有在基础和时间允许时再加入。

## 4. 分层与 MVC

推荐职责划分如下。名称可根据最终语言调整。

| 部分 | 职责 |
|---|---|
| 客户端 View | 展示商品、购物车、订单、售后与主题；收集输入 |
| 客户端 Controller/应用服务 | 响应用户操作，做输入预检查，组织请求，更新界面状态 |
| 客户端通信模块 | 消息编码、连接、超时、读取完整报文、关联响应 |
| 服务端通信/请求分发 | 解码、会话识别、参数校验、调用对应业务 |
| 服务端业务 | 价格裁决、订单状态、库存规则、事务边界与权限 |
| 持久层 | 执行 SQL，把结果映射为对象，封装数据库访问 |
| 数据库 | 保存用户、商品、购物车、订单明细、促销、券与售后 |
| 服务端管理/监控界面 | 可用简易窗口或控制台展示交易与统计；是否单独制作 GUI 待确认 |

MVC 是组织 Model/View/Controller 的一种方式，分层是组织系统职责和依赖的方式。二者可以配合，不能把整个系统机械映射为 UI＝V、数据库＝M 就认为完成 MVC。

界面不直接访问数据库。服务端不接受客户端传来的最终金额作为成交依据。客户端可以展示预估价，但成交金额应由服务端重算，并保存历史价格明细。

## 5. 核心设计思想

### 5.1 用具体变化展示柔性

选择少量扩展点，证明变化发生时影响范围可控：

- 增加一个促销策略，通过新实现和配置接入，保持核心结算流程稳定。
- 更换一套 UI 主题，保持业务规则与通信不变。
- 数据访问集中在持久层，避免 SQL 散落在界面中。

“接口隔离”不是“任何替换都零改动”的保证。数据库方言、事务语义、异步执行方式都可能需要适配。本期不必为展示柔性而同时支持两个数据库、两个语言客户端和分布式部署。

### 5.2 设计模式应解决实际问题

| 机制 | 作用 | 项目证据 |
|---|---|---|
| 策略 | 替换促销算法 | 统一促销接口与打折/直降/券策略 |
| 装饰 | 组织可叠加的价格计算步骤 | 可解释顺序的优惠链与逐步明细 |
| 反射 | 根据受控配置创建已部署的策略类 | 策略配置、工厂、加载验证和错误处理 |
| 观察者 | 分离事件产生方和关注方 | 交易提交后统计/通知监听者，作为可选扩展 |

反射只负责装配，不会自动实现新算法。新增类仍需编写、编译、部署，除非另外明确设计了插件更新机制。策略类来源应由服务端配置控制，不能让客户端任意指定要加载的类。

工厂可以辅助创建策略；单例不是必须考点。共享服务应避免保存某一用户的可变购物车状态，多用户数据必须按用户隔离。

### 5.3 并发正确性优先

多用户不只意味着能开两个窗口，还包括同时结算时不会超卖、不会串购物车、不会重复用券。

正常结算的关键顺序：

1. 识别用户、检查参数和防重标识。
2. 在事务内读取并验证购物车、促销与券，重算应付金额。
3. 按购买数量执行带库存条件的扣减，检查影响行数。
4. 写入订单和明细，核销券，处理本次结算的购物车条目。
5. 任一核心步骤失败则整体回滚；全部成功才提交。
6. 提交后返回成功。统计刷新、非关键提示可异步处理。

不要在订单尚未落库时返回成功，也不要先扣一次库存、再在观察者中扣第二次。数据库提交成功但网络响应丢失时，客户端应能使用同一业务防重标识查询或重试，得到同一订单。

### 5.4 三种“异步”需要区分

- **界面后台执行**：避免网络等待卡住窗口，桌面程序应处理。
- **网络异步请求/应答**：允许多条请求在途并匹配响应，属于通信设计选择。
- **服务端事件异步处理**：事务完成后由工作线程处理通知/统计，属于业务扩展。

使用同步 Socket 并不意味着在 UI 线程阻塞。观察者模式本身也不会创建工作线程。队列是否广播、事件是否可能丢失、失败怎么重试，都需要明确。

若采用内存队列，可将统计限定为可从订单重建的派生信息；不能宣称进程崩溃后仍能保证事件不丢。确实需要可靠事件再引入事务事件表等设计，不把它强加为课程必做项。

## 6. 促销系统的理解方法

原 PPT 提到统一折扣、第 2 件 9 折/第 3 件 8 折或免单、降价、券，以及混合策略。它没有定义精确计算规则。

设计前必须确定：按同一商品还是跨商品计件、折扣是否与直降叠加、券门槛按优惠前还是优惠后金额、优惠顺序、四件以上如何计算、免单究竟针对哪件，以及退货时如何退回优惠后的金额。

用金额示例确定规则比单写“可叠加”有效。例如已经UI12/UI16确认并验证：两件100元商品，先每件直降10元，再九折，得到162元；用优惠后满150减20券，成交142元。改变顺序或门槛口径会改变结果。

金额建议以整数分表达；如用十进制金额，应确定两位小数、舍入模式与逐项/汇总舍入时点。订单保存原价、各优惠步骤、成交金额，不能靠当前商品价格还原历史订单。

UI12/UI14的商品直降/折扣已用于S09：先减最低零，再折扣，逐件HALF_UP到分后汇总。策略负责比例算法，装饰链记录步骤，受控反射只装配允许列表类，总额用精确大整数。管理草稿/预览与保存分开；UI15时间选择由服务端时钟裁决，数据从同一数据库快照读取，后台控制器不阻塞EDT。

完整S10已按UI16/UI17实现：在商品优惠合计后判断券门槛并抵扣，162元用满150减20得142元。券活动先草稿后发布，发布锁定条款，暂停仅影响领取；个人券通过归属和唯一约束隔离，条件增加发放量与写个人券在同一事务完成。领券、只读报价和成交核销是不同动作；报价不可用时应付为空，不静默无券继续。摘要比较变化，S11仍在同一事务重算所选商品并原子核销。S11按UI19/UI20支持卡内勾选和二次确认，只成交所选、保留未选；先查用户+结算键终态，再校验当前车，已知业务失败回滚全部交易操作并保存失败终态。提交前本地记录原请求，丢应答/取消/重启后先核对，不能换键重买；历史单保存原价/优惠/券和实付。UI18券排除商品仅存档，门槛/抵扣细则待讨论，现有全店券继续原条款；阶梯/免单仍为候选。

## 7. 通信协议的理解方法

PPT 第 12 页示例包含 1001、10020001、1003、20020001、2003。可看出请求/应答及商品操作的意图，但不能据此断言所有编码都固定具有“中间位”和“后四位”。

推荐把操作标识与商品 ID 分开：操作表示“加入购物车”，数据体表示商品编号和数量。是否必须兼容原示例，应在正式协议确定前确认。

协议必须能说明编码、报文边界、字段、错误、超时、会话与版本。TCP 是字节流，读取一次不保证得到一条完整业务报文。完整规范和样例放在需求文档或独立协议文件中，避免两份文档各写一套。

## 8. 数据持久化与技术选择

PPT 第 7 页列出 Hibernate/MyBatis 与 MySQL/SQLite 等，第 9 页强调持久层完成映射。不应写成“禁用 ORM”，也不能据此认定只有这些选项合法。

建议优先选择自己能解释的组合。JDBC＋DAO 可清晰展示 SQL 和事务；MyBatis 可减少映射重复。若老师另有框架限制，以明确课程要求为准。

SQLite 适合轻量本地演示，但其写事务存在并发限制，需要明确忙等待、重试与失败处理。换成 MySQL 也不会自动解决所有并发问题。以实际测试说明能力边界。

## 9. 交付与答辩

PPT 第 16 页明确：六次周报告各 5 分、答辩 60 分、最终大报告 10 分，答辩每人 10 分钟。具体日期、模板和“3＋3”含义需查课程通知。

建议准备以下证据：

- 一条完整可演示流程：浏览、购物车、混合优惠、结算、订单查询、售后。
- 两客户端并发购买有限库存的结果，以及重复提交仍只产生一个订单。
- 业务分层、协议、促销类图、结算时序与状态说明。
- 可复现的启动和数据初始化步骤。
- 能亲自讲清关键类、失败处理与选型取舍。

第 17 页提示重视难点、完整性和个人进步，不提供保分公式。报告应记录真实完成内容，未验证项目如实标注。

## 10. 后续顺序

1. 按[开发计划](开发计划.md)一次选择一个小任务，只收口影响本轮的关键决策与验收样例。
2. 检查现有代码和环境，确定一套技术栈。
3. 跑通独立服务端、桌面客户端、数据库商品展示与主题切换。
4. 实现购物车和促销，再实现事务结算、防重与并发测试。
5. 完成售后闭环，按时间评估观察者/异步事件扩展。
6. 整理文档、报告、演示与个人理解。

按用户最新要求，里程碑按可验收步骤推进，不按截止日期或个人技术熟悉度排期。每轮开发后主动记录[当日完成与待办](../开发日志/README.md)，涉及产品范围、主要界面和交易规则的变化先讨论。六次周报告不代表从今天开始必然还有六周。
