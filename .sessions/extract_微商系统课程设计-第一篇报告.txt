一、项目的需求描述
1.1 项目概述与系统定位
本项目拟实现一个运行于 PC 平台的 C/S（客户端/服务器）架构社交电商系统。系统采用单店经营模式，但支持多用户同时访问，从而引出并发处理与资源共享等实际问题。
系统的业务目标不是追求界面华丽，而是完整打通一条电商交易闭环：浏览商品 → 加入购物车 → 应用促销 → 结算下单 → 售后服务 → 界面风格切换。
在架构上的自我约束有四条：
不使用 Web 技术栈：客户端为独立安装的桌面程序，服务端为独立进程，通过 TCP/IP 直接通信，通信协议自定义。
不使用现成框架替代核心机制：分层结构、通信协议、对象与关系数据库映射、并发控制等均从原理层面自行实现，避免被框架封装遮蔽。
限制业务范围：不考虑多商家入驻、真实支付渠道、移动端适配。
明确“不做清单”：多商家入驻、真实支付、移动端、商品评价、收货地址等（属于纯增删改查，不产生架构价值）。

叠加规则：多个促销同时生效时，按固定顺序依次计算：「先打折 → 再满减 → 最后用券」。该顺序写入配置文件而非硬编码，以保证前后端一致。顺序不同会导致计算结果不同，因此必须明确约定并服务端权威执行。

顾客登录后浏览商品 → 加入购物车 → 提交结算 → 服务端校验并扣减库存 → 生成订单 → 返回结果。若有问题，顾客可发起售后申请；店主登录后可维护商品、配置促销、审核售后。

2.3 不熟悉技术的解决路径
针对上述没接触的技术，总体解决思路是：先跑通最小例程，再结合项目迭代深化；不盲目引入框架，优先理解底层原理。重点难点的解决路径如下：
Socket/TCP 通信：先理解 TCP 连接建立与字节流读写，跑通“客户端发一句话→服务端回一句话”的例程，再改造成收发指定长度的字节块。若进度紧张，先实现定长报文加同步阻塞的最简版本保证功能交付，稳定后再升级为不定长报文。
多线程与并发：掌握 Thread/Runnable、synchronized、ReentrantLock，让多个线程同时对同一个库存变量减一，观察竞态条件，再引入数据库条件更新进行修正。库存互斥优先采用数据库条件更新，把并发正确性交给数据库事务保证。
设计模式：只重点学习 5 个模式：策略、装饰、观察者、工厂、单例，另加状态模式用于售后流转。每个模式整理一页笔记，包含意图、类图与一段可运行示例。模式数量不是越多越好，讲清 2 至 3 个与业务紧密贴合的模式远胜于罗列十个用不上的模式。
反射机制：掌握 Class.forName、newInstance、Method.invoke 三个 API。把类名写进配置文件，程序启动时读取配置并反射实例化该类。若反射理解困难，可先用工厂模式加注册表达到同样效果。
JDBC 持久化：先手写 Connection/PreparedStatement/ResultSet 完成一次“对象存成表、表读回到对象”的完整过程，理解映射本质。完全手写 JDBC 封装即可满足要求，MyBatis 仅作为后期演示持久化柔性的对照实现。
桌面 GUI 编程：掌握容器、布局管理器、常用控件与事件监听。界面不追求视觉效果，做到功能可用、结构清晰、业务代码与界面代码分离即为达标。
UML 建模：只掌握四类图：用例图、类图、时序图、活动图。每学一类图，就用本项目的一个真实场景画一遍。

（二）装配流程

关于「策略管组装、装饰管变换」的含义：策略决定链由哪些环节构成，装饰决定链上每一环的变换规则。两者必须分开，因为它们的变化原因不同——增加一种玩法，变的是链的构成；改变优惠的叠加方式，变的是链上某一环的变换规则。变化原因不同，就应当分属两个独立的扩展点。

3.5 并发与互斥的设计
（一）问题的本质
多用户同时抢购同一件限量商品时，若扣减库存的实现为“先查询、再判断、后更新”三步，则在两个线程之间会出现竞态条件，导致超卖。
（二）本系统的方案
采用数据库条件更新：把判断与扣减合并为一条原子 SQL，由数据库事务机制保证原子性。
UPDATE t_product SET stock = stock - ? WHERE id = ? AND stock >= ?
执行后检查受影响行数：返回 1 表示扣减成功；返回 0 表示库存不足，立即回滚事务并向客户端返回库存不足。若一条 SQL 需同时扣减多件商品，则在同一事务内逐条执行，任一条影响行数为 0 即整体回滚。
（三）为什么还需要 JVM 锁
数据库条件更新已经能保证正确性，JVM 层的锁（按商品编号分段加锁）是性能优化而非正确性保证：它可以拦住同一进程内对同一商品的重复请求，减少无谓的数据库往返。必须清醒认识到——JVM 锁只在单进程内有效，一旦服务端部署为多个实例，仅有 JVM 锁就会失效，而数据库条件更新依然有效。这个对比是理解本地锁与分布式锁差异的最好例子。
（四）超卖复现实验
本项目计划把上述问题做成一个可重复运行的实验，作为并发正确性的直接证据：
准备库存为 1 的商品；
编写测试程序，启动 N 个线程（如 50 个）同时对同一商品发起结算；
先运行无保护版本（三步式扣减），统计成功订单数与最终库存，展示成功订单数大于初始库存的超卖现象；
再运行条件更新版本，展示成功订单数恰为 1、其余均返回失败；
记录两次运行的完整输出作为实验数据。
本实验的意义：它不仅是功能验证，更是一次完整的“发现缺陷 → 定位原因 → 提出方案 → 验证修复”的工程过程。

不匹配的表现 | 具体例子
继承关系无处存放 | Java 中不同促销策略是同一父类的子类，数据库只有一张表用 type 字段区分
对象引用与外键 | 对象之间用引用关联，数据库用外键关联（order_id 列）
多对多关系 | 促销与商品是多对多，对象里是 List，数据库里必须拆成三张表
值的粒度不同 | 对象中的金额值对象在数据库里退化为 DECIMAL 字段
机制 | 承担职责 | 解决的问题
策略模式 | 把每种促销玩法封装为独立的策略类，实现统一接口 | 玩法可替换、可新增、互不干扰
装饰模式 | 把多个促销按顺序逐层包裹价格计算 | 玩法可叠加，且叠加顺序可控制
反射 | 依据配置文件中的类名动态创建策略对象 | 新增玩法无需修改任何已有代码
约束 | 说明

收发切分 | 必须按长度字段切分，不得假设一次 read 就是一条完整报文，TCP 是字节流协议
